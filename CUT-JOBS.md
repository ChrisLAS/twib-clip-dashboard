# Disabled inventory cut requests

This isolated slice persists structured owner cut requests alongside existing inventory reviews. It does not activate execution. Syncthing remains the authoritative media location; the dashboard stores request/provenance metadata and plays explicitly selected workstation files.

## Request behavior

Choose **Explicit range** or **Editorial guidance**, then save **Cut down** once. Positive explicit ranges must be at most 180 seconds with millisecond precision. Preserve complete thoughts and qualifications. A start-only or theme request remains editorial `needs_review`; the client never parses old free-text notes into executable cuts.

A missing or unknown `CAPTURE_JOBS_GRANT_OPERATIONS` is closed. `cut` authorizes cut execution only; `capture` authorizes URL capture only; `capture,cut` explicitly authorizes both. The server checks this boundary for owner capture routes, default/explicit machine claims and results resolved by immutable stored job kind, before any replay. Claim expiry cleanup and lease lookup are also restricted by kind. Request-only persistence does not require machine execution authority.

A request binds the existing item/native IDs, observed source version/hash, review revision and decision. Persistence and the review operation commit together. An unchanged uncertain save retains its operation UUID with the draft, including across pagination/filter unmounts. Current-source/current-review/unique-native-identity guards apply inside initial queue and explicit retry transactions. Generic capture retry cannot bypass them.

## Nomad execution and review boundary

`cut_worker.py` resolves exactly one existing local_files/downloaded native identity and requires its current path to equal the episode-relative source. Missing IDs/hashes, duplicate identities, changed source, symlinks, stale episode binding and invalid boundaries refuse execution. No filename guessing creates identities. Only range requests execute.

The existing show lock serializes supported native history writers. Input is pinned, copied into private staging, hashed and checked for change. ffmpeg execution, generated bytes, output duration and full decode are bounded. Publication uses exclusive creation in `new-review/<request UUID>-a<attempt>.mp4` and a receipt; it never overwrites a destination. The child is appended to native `local_files` with immediate parent, source ancestor, source/output hashes and local range. Parent history is preserved; approval is explicitly `unreviewed`, readiness false. Original media, prep, manual layout, player order and set-aside state are not modified.

Partial publication/history failures park for operator reconciliation; no automatic replay, cleanup of published media or promotion occurs. Durable worker/poller journals replay matching claim/result receipts after lost replies. Accepted derivative attachment cannot be erased by stale or concurrent result deliveries and prevents another retry. Each explicit eligible retry uses a new bounded attempt filename.

## Disabled editorial planning transport

Migration `0015_inventory_cut_planning.sql` adds a nullable immutable proposal receipt to existing requests. It does not alter prior migrations, source media, existing grants, or deployed configuration. `CUT_PLANNING_ENABLED` is absent/default closed; planning additionally requires cut requests, capture transport, and an explicit `plan` operation grant. `cut` and `capture` grants do not confer planning authority. Canonical grants can include `capture,plan`, `cut,plan`, or `capture,cut,plan` only when separately authorized.

A first-pass/editorial review stores the original immutable cut request. When planning is enabled, the server queues a separate `kind:plan` wire with `planning.parentVersion`, `reviewRevision`, and SHA256 of the exact original request JSON bytes as `requestRevision`. This wire is claimable only through `job_kind:plan`; it can never enter the range-cut queue. Nomad supplies the trusted local narrative/transcript context, and returns only a proposal and revision digests. Transcript excerpts are not uploaded to this dashboard.

`EDITORIAL_PROPOSAL_READY` is a `needs_review` receipt, not execution or approval. Proposals contain a complete <=180-second range, rationale, source hash and request/context/transcript/binding revisions, `ready:false`, and `approval:unreviewed`. The server verifies source/request identity, lease validity, current observation and review revision, and atomically saves the immutable receipt. Exact delivery retries are idempotent; altered delivery IDs/bodies, stale decisions/sources, and revoked operation grants fail closed. Context and transcript digests are authenticated adapter assertions, not independently reconstructed server-side.

Owner-only `GET /api/inventory/plan-requests/{requestId}/proposal` rechecks current source/review eligibility. It does not itself approve a plan or execute media work. Manual new range decisions still use current version/revision and existing cut guards. The separately gated automatic first-pass transition is described below. Neither path approves the derivative, and originals remain untouched.

## Bounded automatic first-pass derivative (follow-on slice)

Migration `0016_first_pass_derivative_link.sql` adds an immutable, unique source-plan link. The server now supports the finished-first-pass workflow without impersonating an owner session or requesting approval of each timestamp. It is independently disabled by `CUT_FIRST_PASS_AUTO_ENABLED` (absent by default), in addition to all planning and execution gates and BOTH `plan` and `cut` operation grants.

After an authenticated `EDITORIAL_PROPOSAL_READY` receipt, only an original immutable `first_pass` request authorizes the transition. Standalone `editorial` requests do not. The server rechecks current observation/review eligibility and exact proposal source/request hashes, then atomically inserts one deterministic range request and cut job. The UUID is derived from a versioned domain, plan job ID and proposal binding. The new cut carries `editorial:{planJobId,binding,contextRevision,requestRevision}`. Source version and review revision remain unchanged; no owner session is used, no review is approved, and no transcript/context text is transmitted. Both original request and proposal are retained.

The configured Nomad cut worker must find that exact terminal proposal in its private plan journal, verify the proposed range and source, and verify current authoritative context inside the episode lock before any derivative mutation. The separate execution grant and cut gate are still mandatory. Missing/stale journal/context fails closed. Outputs remain `ready:false` and `approval:unreviewed` for final editorial review.

Lost acknowledgements re-enter the transition through the same durable plan receipt. The unique source-plan link and deterministic request prevent duplicate cuts; a transaction failure leaves no partial child request/job. A source or review change before the first transition refuses new work. This slice adds no plan retry or polling scheduler; delivery retry is the existing transport's responsibility. Rollout approval must explicitly include the automatic gate and Nomad journal validation as well as the bounded original first-pass-to-derivative workflow.

### Receiver robustness and acknowledgement boundaries

Authenticated result requests have a 32,768-byte envelope budget only while the planning grant and gate are active. Claim and ordinary create requests retain their 4,096-byte budget. This accommodates Python's ASCII-escaped serialization of 2,000 non-ASCII rationale codepoints; limits are checked on bytes, without truncation. Rationale text is 1–2,000 Unicode scalar values with nonblank content; lone surrogate values are invalid. The producer checks its complete serialized terminal envelope before durable storage.

Stored historical instructions remain readable if native identity evidence is missing, but new execution queue entries and retries require at least one native clip ID/UID matching `[A-Za-z0-9_.:-]{1,128}`. Planning claims use that same stricter executable-parent schema, including the executor maximum source size of 536,870,912 bytes (512 MiB). The inventory response exposes cutFirstPassAutoEnabled only when every required planning/execution/automatic gate is enabled.

Migration `0017_first_pass_transition_outcome.sql` records a distinct `transition_code`. If source/review supersession invalidates the derivative transition after a valid plan receipt commits, that receipt is still acknowledged and replayable. The blocked transition is exposed as `transitionCode`; no cut is created and no recurring terminal delivery is held open solely by that supersession. Transient storage failures still propagate for transport retry. Progress mutations compare the actual lease/state/attempt and current proposal state, so a delayed duplicate progress delivery cannot overwrite a later terminal proposal or derivative outcome.
